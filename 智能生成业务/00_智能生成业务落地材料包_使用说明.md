# 智能生成业务落地材料包

## 这套材料解决什么问题

这套材料用于竞聘结束后的业务对齐、技术验证和团队拆解。核心目标不是继续论证“智能生成值得做”，而是把方向收敛为可以开始执行的计划。

材料由三部分组成：

1. [智能生成业务全景图](./01_智能生成业务全景图.md)：用于和领导、产品、设计及研发统一业务边界和优先级。
2. [天气场景端侧智能调用 PoC 技术方案](./02_天气场景端侧智能调用PoC技术方案.md)：用于启动第一个可量化的技术验证。
3. [智能生成业务六个月路线图](./03_智能生成业务六个月路线图.md)：用于安排阶段目标、工作流、里程碑和停止条件。

已有的 [HarmonyOS 应用服务 Kit API 扁平化与主动服务可行性报告](./HarmonyOS应用服务Kit_API扁平化与主动服务可行性报告.md) 作为能力范围和官方 API 约束的研究依据。

## 建议使用顺序

### 第一步 方向对齐

先使用业务全景图统一以下共识：

- 智能生成组的目标从“根据业务类型匹配模板”升级为“理解场景并提供服务”。
- 近期主线是智能服务 Agent，情感化渲染作为差异化探索。
- API 扁平化不是最终产品，而是将系统和外部能力转化为模型可安全调用的业务能力。
- 信息提取、偏好学习和反馈闭环是两条业务路线的公共底座。

### 第二步 启动天气 PoC

天气场景用来证明以下最小闭环：

```text
原始提示词
  → 领域与能力选择
  → 参数提取
  → 默认值补全
  → API 编排
  → 统一业务数据
  → 卡片或文本结果
```

天气 PoC 不承担主动服务、长期个性化和全量 API 生产线的全部目标。它只验证最核心、最容易被证伪的技术假设。

### 第三步 根据结果进入通勤场景

天气 PoC 达标后，加入日历、位置、地图、通知和实况窗，形成第一个主动服务闭环。若天气 PoC 未达标，应先定位领域选择、参数提取、默认值解析或 API 适配中的具体问题，不直接扩大场景。

## 三个需要持续坚持的边界

### 1 模型负责理解 不直接获得执行权

Jev 或 Laya 类判别模型负责领域和能力选择，生成式端侧模型负责参数提取。权限校验、默认值、用户确认、幂等和实际执行由确定性代码控制。

### 2 主动服务不是后台高频轮询

主动服务优先使用日历、围栏、Push、健康订阅等事件驱动机制。后台任务只做系统允许范围内的补偿，不以常驻进程为前提。

### 3 不以 API 数量作为平台价值指标

首批只建设能支撑高价值场景的业务能力。平台价值应通过任务完成率、能力复用率、接入周期、时延、安全和用户接受度衡量，而不是通过包装了多少个底层函数衡量。

## 建议的第一次团队会议

建议用 90 分钟完成首次对齐：

| 时间 | 议题 | 期望结果 |
|---:|---|---|
| 15 分钟 | 当前业务问题和目标 | 确认不再只以模板命中率作为长期目标 |
| 20 分钟 | 业务全景图 | 确认主航道、探索方向和公共底座 |
| 25 分钟 | 天气 PoC | 确认范围、输入输出、技术分工和验收指标 |
| 20 分钟 | 六个月路线图 | 确认前六周任务和每阶段停止条件 |
| 10 分钟 | 分工与风险 | 确认接口人、设备、权限、数据集和例会机制 |

会议结束时至少要形成四个明确结果：天气 PoC 负责人、首批测试设备、测试集负责人和第一周可演示目标。
