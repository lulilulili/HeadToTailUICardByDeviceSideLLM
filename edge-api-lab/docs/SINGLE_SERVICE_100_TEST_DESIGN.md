# 单服务 1000 条用例：测试设计与解释边界

适用套件：`single-service-100-v1`。本说明只解释正式推理开始前已固定的题组与合同，不提供模型实测分数。本次整理没有读取模型输出、修改金标/源码/网页，或重新运行全语料与模型。

## 1. 测什么，不测什么

本轮验证中文单服务请求能否选对业务领域、选对一个 API，并保真提取用户明确给出的参数；环境参数确实未提及时，才允许使用声明的手机环境 mock。一个 API 的整体对象、多字段结果或单次多字段更新仍是单服务，不属于组合执行。跨服务编排、多步任务、unsupported 场景不在本题组内。

10 个领域各 100 条，共 1000 条；同一套题依次测 `qwen2.5:1.5b`、`qwen2.5:3b`、`qwen2.5:0.5b`，计划 3000 条正式调用，预热另存且不计分。7B 不参加本轮。每个模型使用相同的固定题序，每连续 10 条各包含一个领域；这不是对真实用户分布的随机采样。

题组覆盖现有 417 个注册 API 中的 248 个不同 API。每域 100 条是在 API 区分与表达变化之间作取舍，既不是每个 API 都有题，也不是每个 API 都有同等样本量。未覆盖 API 不能据此判断支持或不支持。

## 2. 金标来源与状态分布

每域 001–010 是既有开发用例，共 100 条，标记 `previous-100-development`；011–100 是推理前固定的新增用例，共 900 条，标记 `new-900-fixed-before-inference`。既有题保留原 ID 引用。新题按当前注册输入、API 语义及 resolver 合同逐例编写，提供槽的类型与预期状态已作静态合同校验，不是拿 grounding 输出或模型回答反推答案。

| 冻结金标状态 | 条数 | 含义 |
| --- | ---: | --- |
| `ready_mock` | 901 | 当前合同可以生成合法 mock 执行计划，不等于真实业务已执行成功 |
| `needs_clarification` | 77 | 存在必需业务参数/目标缺失，或当前语法/角色合同需要澄清 |
| `resolution_failed` | 22 | 所需环境/地理编码等依赖在声明上下文中不可用，不能用猜测替代 |

这些数字是 1000 条**预期状态分布**，不是三个模型的成绩。工程题组并非独立人类盲测，也不是随机人类提示词测试；开发方知道接口与规则，旧 100 条已参与开发，新 900 条即使推理前固定，也不能直接称为生产成功率或无偏泛化评估。

## 3. 天气、日历、联系人的设计

下表中的 API 数包含每域既有 10 条与新增 90 条；后两列仅描述新增 90 条的设计规模。scenario/category 是作者的工程标签，并非统计上彼此独立的自然语言类别。

| 领域 | 合并后不同 API 数 | 新增 scenario 数 | 新增 category 数 |
| --- | ---: | ---: | ---: |
| weather | 72 | 55 | 15 |
| calendar | 41 | 76 | 18 |
| contacts | 50 | 85 | 11 |

### 天气

覆盖实况、逐小时、逐日、分钟降水、预警、生活指数、潮汐和城市信息；既有整体对象读取，也有深字段选择。`weather.query` 的单次 `data_needs` 多字段请求保留，不能拆成多个业务 API 来获得额外得分。

表达维度包括口语温度、相对时间、无位置/无时间、显式地点、否定干扰、精度要求、结构化列表、整体与深字段的区分，以及中文全球冷门地点。不是把同一个天气句式重复 90 次、只替换城市。

| 用例 | 提示词摘录 | 检查点 |
| --- | --- | --- |
| `e100-weather-011` | 这会儿上海有多热？我只要实况温度。 | 口语字段与实况 API；当前金标只标地点，“这会儿”未单列 `time_ref`，勿把此题算作口语时间提取覆盖 |
| `e100-weather-012` | 不要看北京，查广州此刻的体感温度。 | 被否定的北京不是当前目标，体感温度不是普通温度 |
| `e100-weather-013` | 现在空气湿不湿？给我相对湿度数值。 | 用户未说地点才允许模拟手机位置补全 |
| `e100-weather-024` | 请返回实况天气图标资源。 | 没有用户时间/地点参数；图标字段不能当作地点 |
| `e100-weather-081` | 日粒度查广州明天的气温和降水，data_needs=["temperature","precipitation"]。 | 单 API、多字段、日粒度与列表类型 |
| `e100-weather-082` | 把武汉现在完整的实况天气对象给我，不限某个字段。 | 整体对象 API 与单字段 API 区分 |

### 日历

覆盖搜索、创建、更新、取消，以及事件字段、重复规则、提醒、日历账户/配置的读取和单字段写入。创建/更新参数包含标题、开始时间、业务地点、持续时长、提醒与布尔值，测试 `0`/`false` 不被当作“未给”。标题或地点是业务内容，不可从系统生成默认值；开始时间也是必需业务值，不能用当前时刻代替用户未提供的开始时间。

只读请求可在明确可信的选中对象上下文中读取对应 ID；更新/取消不能把“当前选中”的 ID 静默变成写目标。已有 ID、缺 ID、缺标题/时间、明说的时区与未提的时区分别覆盖。

例如：`calendar-040` 读取 `ev_120` 的重复间隔；`calendar-050` 只读当前选中事件的地点名称；`calendar-054` 新建日程的地点是“实验楼 B-204”，不是手机位置；`calendar-068` 请求创建但标题/开始时间未给，应澄清；`calendar-080` 明确修改为 `Europe/London`，不能被环境时区覆盖；`calendar-088` 是将全天标记写成 `true` 的一次字段更新。

### 联系人

覆盖姓名/号码等搜索、完整详情、电话号码/标签及其他对象的深字段读取，联系人创建/更新与单字段写入。强调 `query` 与 `contact_id` 的角色、电话字符串保真、生日不猜年份、对象/列表字段的类型，以及未给必需姓名或写目标时不补默认业务值。

例如：`contacts-011` 的“通讯录里有叫‘许宁’的人吗？”是姓名查询；`contacts-035` 要电话号码值、不要标签；`contacts-058` 的“10月12日”不补生日年份；`contacts-070` 的 `+86 21 5555 0301` 保留号码中的空格；`contacts-089` 把昵称“晴天”当写入值，而不是天气请求；`contacts-100` 是完整详情 API。

`contacts-060` 的备注原文为“明天去北京查天气；只是备注”。这是单次联系人创建的载荷，不能据正文里的天气/时间/地点调用天气 API，或把正文地点拿去补环境。

## 5. 已知合同边界：安全拒绝不等于理解完成

天气／日历／联系人新增题中，20 条另带 `userGoalStatus: ready_mock` 与 `contractBoundary`。这些题的实际目标足够明确或合理，但当前合同不能完成；必须单列，不能靠“正确拒绝”宣称已支持自然表达。

| 用例/范围 | 用户已提供什么 | 当前金标 | 未完成原因 |
| --- | --- | --- | --- |
| `e100-weather-054` | “未来半小时”降水类型 | `needs_clarification` | 当前 `readTime` 未支持此时间表述，不是用户没给时间 |
| `e100-calendar-056` | 标题“签到”、开始时间“明早九点”、开始时提醒 | `needs_clarification` | 当前 datetime 未把“明早九点”解析为上午九点 |
| `e100-calendar-057` | 全天 `true`、明确开始日期 `2026-10-12` | `needs_clarification` | 当前 datetime 未结合全天标记接受日期作为全天开始值 |
| `e100-weather-059` | 严格未来 15 分钟降水强度，不允许降精度 | `needs_clarification` | 此题上下文明确 `minute: false`，不能以小时结果冒充分钟结果 |
| `e100-weather-085`–`e100-weather-100` | 16 个中文命名地点与目标天气字段 | `resolution_failed` | 此题上下文清空 `geocodes`，没有可信地点解析结果；不允许替换模拟手机所在地 |

16 个地点来自 [全球中文地名样本](../data/global-city-samples.json) 的 GeoNames `alternateNames` 明确 `zh` 语言标签，保留 sample ID/source field，分布于六洲。例子是“查沙基索现在的气温”“曼科拉当前空气质量类别是什么”。地名来源可追溯，但样本坐标不注入运行 geocode，题目刻意验证“明确地点尚未解析”与“没有说地点”是两回事。这 16 题也不能证明任意全球地点均已正确识别或已完成真实地理编码。

上述安全拒绝之外，还有真实缺必需业务槽、写目标不明确等 `needs_clarification` 题；两者在后续错例分析中应分开。不能为降低澄清率，改成默认标题、当前时间、随机 ID 或当前位置。

## 6. 环境与 mock 的边界

固定基准时间是 `2026-10-10T08:00:00+08:00`，时区 `Asia/Shanghai`；模拟手机当前位置是上海固定坐标 `(31.2304, 121.4737)`，来源 `fixture`。基准网络句柄为 `23`、音频流为 `MUSIC`，同样明确标记为评价 fixture；单条题的 `context` 可清空/覆盖这些依赖。

“本机位置”指手机而非运行实验台的电脑。不读取浏览器定位或电脑 GPS，未连接 Harmony 真机，不把 mock 时钟/电量/网络/音量称为系统实测。业务 API 是伪 API/mock；尤其地理编码 `ready_mock` 只表示计划合法，不代表真实地址/经纬度已经查得。

金标的 `expected.arguments` 是用户给的槽，不要求把环境补全值塞入原始提取答案。用户明确值优先，未知地点原文不能丢；地理编码不可用应失败或澄清，而非回退当前位置。环境补全与业务默认值的权限不能混用。

## 7. 正式结果应如何阅读

- 分别看领域、API、原始参数与最终执行语义；规则修复后的通过不等于模型原始提取变好。合法 JSON 中可解析的正确 API 单列 `parsedApi`，但 schema 失败不计正式 API 正确。
- `semantics` 包含正确澄清/解析失败，不能叫“服务执行成功率”。`readyRequestSemantics` 只看金标可执行题；`safeNonReady` 只看金标非就绪题；已知合同边界仍需阅读其实际用户目标。
- 旧 100 与新 900 分开报。一个域/模型未完成时计划仍为 100/1000，准确率分母只用已完成调用；失败调用计分，未完成调用不当作 0 分，空分母是 `null`。
- 主错因按 provider/rule 错误、领域、API、gold 合同、参数、最终状态/约束排序；候选召回失败与召回后选择错误分开。一次调用可有多处参数差异，不能把差异总数相加当失败调用数。
- 三模型同题序便于配对比较，但仅各一次正式调用、同一固定 fixture，不能据此估计随机采样稳定性或真机生产收益。

本说明记录测试设计，不在推理过程中调整题目、提示词或参数规则；后续分析应引用冻结快照与逐例原始证据，另列模型问题、后处理问题、合同限制及 mock 依赖缺失。
